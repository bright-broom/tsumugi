# 問い合わせ情報の所在・保持・削除

問い合わせフォームから預かる情報が、どこに、どれだけの期間残り、どう消すかの一覧。判断の理由は [ADR 0034](architecture/0034-inquiry-access-and-retention.md)、受付の仕組みは [ADR 0032](architecture/0032-inquiry-intake-service.md)・[ADR 0033](architecture/0033-dual-notification-and-reply-deadline.md)。

> 受付サービスはまだ配備していない。下の表は実装した仕組みと、配備時に守る前提を書いたもの。実在の保存先・送信先はまだない。

## 所在の一覧

| # | 場所 | 残る情報 | 見られる人 | 保持と削除 |
|---|---|---|---|---|
| 1 | 受付の保存先（`InquiryStore`） | 入力 6 項目（お名前・お店の名前・業種・電話・メール・内容）、受付番号、受付日時、入力の指紋（SHA-256）、通知の状態、返信の記録、契約状態、法的な保全 | 担当者 2 名（窓口 `createInquiryDesk` 経由）。保存先の事業者（委託） | 保持期限の処理で削除（下の表）。指紋も記録と一緒に消える |
| 2 | 通知メール（担当者の受信箱、送信事業者の送信記録） | 受付番号・期限と入力 6 項目 | 受信箱の持ち主、送信事業者 | **削除処理では消えない。** 下の「削除の手順」で受付番号を検索して消す。事業者の送信記録の保持期間は採用時に確認する |
| 3 | 通知 LINE / SMS（トーク・メッセージ履歴、事業者の記録） | 受付番号と返信期限だけ（個人情報を送らない） | 受け取った担当者、事業者 | 個人情報がないので削除の対象外 |
| 4 | 閲覧・変更の履歴（`AccessLog`） | 時刻・担当者 ID・操作・受付番号・結果・理由の区分 | 管理者 | 個人情報を含まない。保持期間は未決（オーナー判断） |
| 5 | レート制限の記録 | 接続元をハッシュにした値と回数 | なし（処理だけ） | 制限の時間枠が過ぎると消える。IP アドレスそのものは保存しない |
| 6 | 配備先のリクエストログ | 事業者が記録する IP アドレス・時刻など。受付サービスは入力内容をログに出さない | 配備先のアカウントの管理者、事業者 | 事業者の保持期間による。**プライバシー表示に記載がない**（要判断） |
| 7 | バックアップ（週次、#31） | 1 と同じもの | バックアップの管理者 | 1 で削除しても、バックアップの保持期間が過ぎるまで複製が残る。**期間は未決・表示に記載がない**（要判断） |
| 8 | 担当者の端末（メールソフト・電話の履歴・返信の文面） | 返信に使った連絡先と内容 | 担当者 | 表示では「画面の自動ロックと暗号化」。リポジトリからは確認できない |
| 9 | 利用者のブラウザ | 送信した入力。受付障害の画面には送ろうとした内容を表示する | 利用者本人 | サイトも受付サービスも Cookie・保存領域を使わない |
| 10 | ローカル開発のファイル（`FileInquiryStore`、既定は Git 管理外の `.artifacts/`） | 開発用の入力 | 開発者 | 実データを入れない。テストはダミーの値（`example.com`・`000-0000-0000`）だけを使う |

## 保持期限

| 記録 | 削除してよくなる時刻 | 設定 |
|---|---|---|
| ご契約に至らなかった問い合わせ | 最後のやり取りから 1 年 | `INQUIRY_RETENTION.prospectYears` |
| ご契約中 | 削除しない | — |
| ご契約の終了後 | 終了日から 7 年 | `INQUIRY_RETENTION.afterContractEndYears` |
| 迷惑投稿の疑い（隠し項目に入力あり） | 受付から 30 日 | `INQUIRY_RETENTION.suspectedSpamDays` |
| 法的な保全の対象 | 保全を解くまで削除しない（例外として記録） | 窓口の `placeLegalHold` / `releaseLegalHold` |

## 削除の手順

1. 管理者が窓口の `runRetention(管理者ID, { dryRun: true })` を実行し、削除の対象（受付番号と理由）・例外・残す件数を確認する。
2. 対象に疑問があれば、その記録に法的な保全を付けるか、契約状態を直してから 1 に戻る。
3. `runRetention(管理者ID, { dryRun: false })` を実行する。削除できなかった記録は結果の `errors` と履歴に残るので、原因を直して再実行する。
4. 結果の `deleted`（受付番号の一覧）を使い、通知メールを受信箱と送信事業者の管理画面から削除する（所在の 2）。
5. バックアップは保持期間の経過で消える。期間内に復元した場合は、復元後に 1〜4 をやり直す。
6. 定期実行にする場合は、スケジューラ用の ID で `runRetention` を呼ぶ（担当者の 2 名の枠を使わない）。4 と 5 は人の作業として残る。

### ご本人から削除を求められたとき

1. 受付番号か連絡先で記録を特定する（閲覧は履歴に残る）。
2. 窓口の `erase(管理者ID, 受付番号)` を実行する。契約中・契約終了後の保管期間内・法的な保全中の記録は削除されず、理由が返り、履歴に「refused」として残る。その場合は、保管が必要な理由をご本人に説明する。
3. 削除できたら、上の手順 4〜5 と同じく通知メールとバックアップの複製を扱う。
4. プライバシー表示の約束どおり、1 営業日以内に結果を返信する。
