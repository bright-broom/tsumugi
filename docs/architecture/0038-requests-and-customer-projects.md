# 0038 — 修正依頼と顧客・案件の進行は、顧客ごとのファイルと状態遷移の検査で管理する

日付：2026-09-16。状態：採用。関連 Issue：[#26](https://github.com/bright-broom/tsumugi/issues/26)（修正指示・依頼受付・作業時間）、[#27](https://github.com/bright-broom/tsumugi/issues/27)（顧客管理と案件の進行）。共通の置き場所・データの扱いは [ADR 0036](0036-internal-ops-tools-and-estimates.md)。

## 背景

料金表は「整える」月 30 分、「育てる」月 90 分の変更枠を約束し、作業は月の合計を 5 分単位で扱い、依頼ごとに切り上げない。ガイドラインは依頼窓口の一本化と、毎月の作業時間の報告を約束している。画面上で直したい箇所を指定する「修正指示ツール」も作る予定になっている。

顧客が自分で依頼を書き込む画面には、顧客ごとのログインと閲覧権限が要る。ホスティングと認証方式が決まっていないので、今回は作らない。

## 決定（#26 修正依頼）

- 依頼は顧客ごとの `requests/<顧客ID>.json` に記録する。1 件の依頼は次を持つ。
  - URL（http(s) だけ）、画面上の位置（CSS セレクター・座標と画面幅・説明のどれか。1 つは必須）、説明、添付の**参照**（ファイル本体は持たない）、受付経路
  - 状態（受付 → 着手 → 確認待ち → 完了。確認待ちからは差し戻しで着手に戻せる）と、状態ごとの履歴（日時・記録者・メモ）
  - 担当と期限、作業時間の記録（日付・分・作業者）、完了連絡の記録
- 状態遷移は表で定め、飛ばす・完了から戻す遷移を拒否する。完了した依頼をやり直す場合は新しい依頼にする。
- 作業時間は着手後だけ、受付日以降の日付で記録する。
- 月の作業時間は、月の合計を 5 分単位で切り上げる。3 か月平均は 3 か月とも月初から記録している場合だけ出す。記録開始日（`trackingSince`）より前の月は「未記録」で、0 分とは扱わない。
- 変更枠は `src/content/prices.ts` の `RUN` の `minutes` をキーで引く。
- 完了連絡は「連絡した」という記録だけで、ツールからは送らない。
- ファイルの中の依頼の顧客 ID と、ファイルの顧客 ID が違えば読み込まない。

## 残したこと（#26）

- 顧客が画面上で箇所を指定して依頼を送る画面（注釈の UI）。公開サイトは JS 0 バイトなので、サイトに組み込まず別の画面として作る必要があり、ホスティングと認証方式の決定が要る。今回の位置の形（セレクター・座標・画面幅）は、その画面から記録を渡すときの受け口として使える。
- 顧客ごとのアクセス権限。CLI はオーナーのローカル環境で使う前提で、顧客に直接は開放しない。
- 完了連絡の実送信（メール・LINE）。通知の方式（#11）が決まってから、アダプタを通して足す。
