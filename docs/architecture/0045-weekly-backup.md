# 0045 — 毎週のバックアップと復元テスト

日付：2026-09-16。状態：採用（リポジトリの内容について）。保管先の独立性とデータの保管は未決（オーナー判断）。関連：[#31](https://github.com/bright-broom/tsumugi/issues/31)、[#33](https://github.com/bright-broom/tsumugi/issues/33)。

## 背景

運用プランと契約の下書きに「週次バックアップの確認」を書いているが、対象・保管先・保持期間・復元の確認がなかった。Git でソースは管理しているものの、GitHub 上のリポジトリだけでは、履歴を含めた取り出しと復元が実際にできるか、どれだけ時間がかかるかを示していない。

## 決定

### 対象と除外

| 区分 | 対象 |
|---|---|
| ソース | `src/`・`tools/`・`tests/` |
| 素材 | `src/assets/`（公開前の元画像）・`public/`（配信する素材、OGP 画像を含む） |
| 文書 | `docs/`・ルートの `*.md` |
| 設定 | ルートの設定ファイル・`config/`・`.github/`・`package-lock.json` など |
| 履歴 | HEAD までの全コミット |

**Git が追跡しているもの全体**を対象にする。除外は `.gitignore` が正本で、バックアップのスクリプトは次が追跡されていたら作成を止める（二重の防御）：`.env*`（`.env.example` を除く）・`.vercel/`・`node_modules/`・生成物（`out/`・`.next/`・`.artifacts/`・`coverage/`・`public/theme.css` などビルドが書くファイル）・鍵ファイル。あわせて、秘密鍵や GitHub・AWS などのトークンの形をした文字列、未コミットの変更があっても止める。

### 形式

`npm run backup` が次の 3 ファイルを 1 つのディレクトリに書く。

- `repo.bundle`：`git bundle`。単体で `git clone` できる
- `manifest.json`：コミット、区分ごとの件数とバイト数、除外の規則、全ファイルの SHA-256
- `SHA256SUMS`：バンドルと目録のチェックサム（`shasum -a 256 -c` でも照合できる）

### 復元テスト

`npm run backup:restore-test -- --backup <dir>` が、チェックサムの照合 → 別ディレクトリへの clone → 全ファイルのハッシュと目録の照合（除外対象がないことも） → 依存の用意 → `npm run build` の順に行い、段階ごとの所要時間を `restore-report.json` に書く。1 段階でも失敗したら止まり、終了コード 1。

依存の用意は既定で `npm ci`（別環境での復元と同じ）。ディスクが限られる手元では `--deps link`（`package-lock.json` が同じときだけ既存の `node_modules` を参照）を使えるが、所要時間にインストールを含まないことを記録に残す。

### 週次の実行と保持

`.github/workflows/weekly-backup.yml` が毎週月曜 3:23（日本時間）に、バックアップ → 復元テスト（`npm ci` とビルドを含む） → 成果物（Artifact）として保存、を行う。

- 保持期間は 90 日（週 1 回で約 13 世代）。リポジトリの設定で短くしている場合はそちらが優先される。
- 失敗は GitHub の標準の Actions 失敗通知で知らせる。履歴は Actions の実行一覧とジョブの要約（各段階の秒数）。
- `permissions: contents: read`、チェックアウトの認証情報は残さない。秘密情報は使わない。
- 成果物のアップロードは `actions/upload-artifact` をタグ（`v4`）で参照している。作業環境からコミット SHA を確かめられなかったため、他の action と同じ SHA 固定は Dependabot（github-actions）の更新か、オーナーの確認で行う。

### Public リポジトリでの制約

**Public リポジトリの成果物は、リポジトリを読める人なら取得できる。** 保管してよいのは既に公開しているリポジトリの内容だけで、この仕組みは「中身を守る」ものではなく「取り出して復元できることを週次で証明する」ものとして扱う。

- **今後の CMS のデータ（#15 など）や問い合わせのデータ（#10・#33）を、このワークフローの成果物・リポジトリ・その他の公開された保管先に置いてはいけない。** 個人情報を含むため、アクセス制限と暗号化、保持期限と削除（プライバシーポリシーと #33 の決定に合わせる）ができる非公開の保管先が要る。
- GitHub の成果物はリポジトリと同じ GitHub 上にあり、**独立した保管先ではない**。アカウントやリポジトリを失うと一緒に失われる。
- Public リポジトリでは、動きのない期間が続くと定期実行が止まり（GitHub の案内では 60 日）、成果物は 90 日で消える。長く更新しないと手元に世代が残らなくなるため、月次の確認で実行履歴を見る。

### オーナーの判断に残すもの

1. 独立した保管先（GitHub 以外）をどこにするか。候補の例：オーナーが管理する外部ディスクに `npm run backup` の出力を週次で写す、オーナー名義のクラウドストレージ（非公開・暗号化）。費用と条件は採用時に確認する
2. CMS・問い合わせのデータの保管先・暗号化・保持期間・削除の手順（#15・#33 と合わせて決める）
3. 顧客サイトでの対象（顧客の素材・管理データ）と保持期間、復元作業の範囲（契約書の文言との整合）
4. 失敗通知を受け取る人（定期実行の失敗通知は、cron を最後に変更した人に届く）

## 通知は GitHub の標準で足りるか

週次のバックアップについては、**紬の自社サイトのリポジトリに限れば足りる**。失敗しても元のリポジトリが残っており、次の週か手動実行で取り直せるため、即時の通知は要らない。一方、通知は 1 人にしか届かず、定期実行が止まったこと自体は通知されない。顧客データを扱う段階では、保管先の選定と一緒に通知の方法も見直す。
