# 0046 — 公開後の監視を GitHub Actions の定期実行で始める

日付：2026-09-16。状態：採用（紬の自社サイトの公開時点まで）。関連：[#32](https://github.com/bright-broom/tsumugi/issues/32)、[ADR 0044](0044-live-domain-checks.md)。

## 背景

運用プランには定型監視と障害時の一次切り分けを書いているが、公開後の稼働・証明書・検索エラー・表示速度を継続して確かめる仕組みはなかった。検査（`npm run verify`）はビルド時の手元の計測で、公開後の状態は分からない。本番 URL はまだなく、Search Console などオーナーのアカウントが要るものはリポジトリから確認できない。

リポジトリは Public で、GitHub Actions の標準の Runner は無料で使える。有料の監視サービスや有料の Runner は使わない。

## 決定

### 自動で見るもの

`npm run monitor -- --url https://<ドメイン>`（`tools/ops/site-checks.ts` の `checkMonitor`）。検査の部品は公開直後の確認（ADR 0044）と共有する。

| 項目 | WARN | FAIL |
|---|---|---|
| 死活（トップページ） | — | 200 でない・接続できない（15 秒で打ち切り） |
| 証明書の残り日数 | 21 日未満 | 7 日未満・検証できない |
| robots.txt | — | 200 でない・全体の拒否・Sitemap がこのドメインでない |
| sitemap.xml | — | 200 でない・`<loc>` がない・ほかのドメイン |
| 掲載 URL の状態 | — | 1 件でも 200 でない |
| 応答時間 | 1 ページでも 3,000ms 超 | — |

しきい値は障害を見つけるための運用上の値で、測定結果ではない。応答時間は GitHub の実行環境から取得した時間で、利用者の表示速度（LCP）を表さないため WARN に留める。

`.github/workflows/site-monitor.yml` が毎時（17 分）に実行する。

- **リポジトリ変数 `SITE_URL` が未設定なら、依存も入れずに成功で終わる**（ジョブの要約に「未設定」と書く）。URL は公開情報なので Secret ではなく Variable に置く。秘密情報は使わない。
- FAIL があればジョブが失敗する。**通知は GitHub の標準の Actions 失敗通知**、履歴は Actions の実行一覧・ログ・ジョブの要約（結果の表）で、保持期間はリポジトリの設定に従う。
- `permissions: contents: read`、チェックアウトの認証情報は残さない。

### 手順として残すもの（オーナーのアカウントが必要）

- Search Console の登録（DNS の TXT レコードで確認し、サイトの HTML は変えない）、sitemap の送信、インデックス登録のエラー、ウェブに関する主な指標（実データ）
- ドメインの有効期限と自動更新（レジストラの画面）
- 監視の担当者と通知を受け取るアカウント

手順と記録欄は [operations.md「公開後の監視」](../operations.md#公開後の監視) に置く。

### 手元の計測と公開後の実測を混ぜない

`src/content/measurements.ts` の `LCP_SECONDS` は `npm run verify` がローカル配信の Chromium で測った値（手元の計測）。公開後の実測は Chrome UX Report 由来の Search Console・PageSpeed Insights の値で、利用者の端末と回線を含み、アクセスが少ないと表示されない。サイトに載せる数字は出所を分けて書き、実測が取れるまで実測値として扱わない。監視の応答時間はどちらにも使わない。

## GitHub の標準の通知で足りるか

**紬の自社サイトを公開する時点では足りる。顧客サイトの「定型監視」としては足りない。** 理由：

- 定期実行の失敗通知は、ワークフローの cron を最後に変更した人に届く。受け取る人は 1 人で、顧客や 2 人目には届かない。通知の方法（メール・Web）はその人の GitHub の通知設定に依存する。
- 復旧の通知はない。失敗が続くと実行ごとに失敗通知が届く。
- 定期実行は混雑時に遅れることがあり、分単位の検知は約束できない。
- Public リポジトリでは、リポジトリに一定期間（GitHub の案内では 60 日）動きがないと定期実行が自動で止まる。監視が止まったこと自体は通知されないので、月次の確認で実行履歴を見る。
- 実行環境の場所は選べず、応答時間は国内の利用者の体感と一致しない。

顧客向けに監視を提供する前に、通知先を複数にする方法（外部の監視サービスや通知の転送を含む）と、その費用・条件をオーナーが決める。料金はこの文書に書かない（採用時に確認する）。

## 検証の範囲

- 単体テストで、正常時の 6 項目、遅いページの WARN、停止時（503）の FAIL を確認した。
- `out/` を読む模擬配信で `npm run monitor -- --dist` を実行し、正常時の合格と、ページ削除・robots の全体拒否を加えた複製での FAIL（終了コード 1）とジョブ要約の書き出しを確かめた。
- ワークフローは YAML として読めることだけを確認した。push していないため GitHub 上では未実行。実ネットワーク経由の取得も作業環境の制約で未実行。
