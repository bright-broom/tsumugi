# 0002 `src/` を層に分け、案件ごとに差し替える中身を `content/` に集める

- 状態：置き換え（[0004](0004-content-and-routing.md)、2026-09-14）

## 背景

事業の前提は「自社サイトを1号案件にして、2件目以降は中身を差し替えて作る」（[なぜこの形にしたか](../README.md#なぜこの形にしたか)）。
移行直後の `src/` は、屋号・料金・ページ本文・アイコンの形が `data/` に、汎用の小道具と案件固有の図が `lib/` に混ざっていて、
何を差し替えれば別の案件になるのかがディレクトリから読めなかった。import も相対パスで、置き場所を変えるたびに書き換えが要った。

## 決定

- 依存は `pages → layouts → components → content → lib` の一方向。右は左を import しない
- 案件ごとに差し替える中身（屋号・料金・ナビ・業種・仕様・図）は `src/content/` に集める
- 何にも依存しない小道具（HTML の流し込み・アイコンの形・丸め・検査結果の読み込み）は `src/lib/` に置く
- `src/` の中は `@/…` で import する
- `npm run check`（`scripts/check-structure.ts`）が、向きの崩れと相対パスの import を落とす

## 検討してやめたこと

- **`site/` をリポジトリ直下に平坦化する。** 直下には事業の文書もある。アプリを `site/` に閉じておけば、Node・Next.js の生成物が文書と混ざらない
- **共通部分を別パッケージ（npm workspaces）に切り出す。** 顧客サイトがまだ1件もない。2件目ができた時点で、`content/` を境にそのまま切り出せる

## 結果

- 別の案件を作るときに差し替えるのは `src/content/` と `src/pages/`（と `scripts/og.ts` の文面）
- 部品と器が `content/` から読むのは `config`・`nav`・`prices` の3つだけ。別の案件でもこの3つの export の形を保つ
- この変更の前後で、ビルドの出力（49ファイル）はバイト単位で同一だった
