# 0076 本番の配信内容と main のビルドを自動で照合する

- 日付：2026-09-18
- 状態：採用（GitHub への反映・初回実行は status.md 参照）

## 背景

これまでの作業記録は毎回「PR は MERGED、本番反映は未確認」で終わり、本番が main と同じかは担当者が手作業で `check:release` を実行するまで分からなかった。2026-09-18 の PR #87（料金再設定）も、merge commit `79f2983` のツリーから手元でビルドし、本番の52ファイルと公開トップを照合して初めて反映を確定できた（PASS 54 / FAIL 0）。

毎時の Site monitor は死活・証明書・ページ一覧・ヘッダー・参照資産を確認するが、本文・価格・規約が古い版のままでも合格する。`npm run deploy:production`（`vercel --prod`）は手元の作業ツリーを main を経由せず本番へ出せるため、Git 配備の失敗・手元からの配備・巻き戻しで本番が main からずれても、現行の監視では検出できない。

## 判断

`.github/workflows/release-check.yml` を追加し、main をきれいな状態からビルドした `out/` を比較元として、ADR 0068 の `check:release` で本番の全ファイルと公開トップを SHA-256 照合する。

- main への push：Vercel の配備切替を最大900秒・30秒間隔で待つ。全件一致した時点で成功、期限切れは最後の結果を FAIL として残す。
- 毎日 6:41 JST：配備後に main 以外の内容へ変わった状態を検出する。
- 手動実行：配備の直後や障害対応の確認用。

照合の再試行は `waitForRelease`（`tools/ops/release.ts`）に置き、試行回数・経過秒を「照合の試行」として結果の先頭に記録する。比較元の指紋違い・隠しファイル等の入力の誤りは例外のまま再試行しない。CLI は `--wait-seconds`（既定0＝従来どおり1回）と `--interval-seconds`（既定30、待つときは5以上）を受け付ける。`--url` を省略した場合は環境変数 `SITE_URL`、なければ監視と同じ `monitorTarget` の規則で自社公開判断に一致する DOMAIN を使い、未認可の公開先を推測しない。

比較元を「配備に使った実物」ではなく CI の再ビルドにしてよい根拠：ビルド出力が環境で変わるのは `works.html` の検証件数だけで、同一コミット・未コミット差分なし・全項目の検証レポートがある場合に限られる（ADR 0025）。Vercel の配備（`npm run validate`）も CI の `npm run build` もそのレポートを持たないため、ともに「—」になる。2026-09-18 に macOS・Node 25 でビルドした `out/` が Vercel（Linux）の本番とバイト一致したことも確認した。

## 限界と運用

- 一致は「本番の配信内容が main のビルドと同じ」ことの証明であり、配備ID・production alias・commit の API 照合ではない。比較元にない余分な公開ファイルも検出しない（ADR 0068 の残課題のまま）。
- オーナーが ADR 0025 の手順で検証件数入りの `out/` を配る運用に切り替えた場合、`works.html` の1件が不一致になる。その場合は比較元を配備した実物へ変えるか、この照合の対象を見直して ADR を更新する。
- 不一致・取得失敗はジョブの失敗として GitHub の標準通知で知らせる。自動の配備・巻き戻しは行わない。原因の切り分け（配備の失敗、手元配備、CDN の切替遅延、ビルド条件差）は証跡の JSON と Vercel の配備一覧で人が行う。
- 待ち時間の上限は GitHub Actions の実行時間を消費する。本番が長時間ずれている場合、日次の実行も毎回15分待ってから失敗する。

## 検証

`waitForRelease` の一致までの再試行・間隔・期限・1回だけの照合・入力の誤りを再試行しないこと・間隔0の拒否、CLI の待ち時間付き照合と URL 省略時の既定・不正な待ち時間の拒否をテストした。実際の本番に対する照合と故障注入の結果は [status.md](../status.md) に記録する。
