# 0036 — 社内ツールを tools/ops の CLI とし、見積もりは公開料金だけで計算する

日付：2026-09-16。状態：採用。関連 Issue：[#25](https://github.com/bright-broom/tsumugi/issues/25)（見積もり）、ほかの社内ツール [#24](https://github.com/bright-broom/tsumugi/issues/24)・[#26](https://github.com/bright-broom/tsumugi/issues/26)〜[#30](https://github.com/bright-broom/tsumugi/issues/30) の共通基盤。

## 背景

ガイドライン 10.5 は、leadfinder・見積もり・修正指示・顧客管理・月次レポートを「作る予定」としている。どれも顧客・見込み客・売上の実データを扱う。一方でこのリポジトリは Public で、公開サイト（`out/`）は実行時 JS 0 バイトを約束している。

画面つきの管理ツールを作るには、ホスティング先と認証方式（誰が・どの顧客のデータを読めるか）を先に決める必要がある。これはオーナーの判断で、まだ決まっていない。

## 決定

### 置き場所と実行方法

- 社内ツールは `tools/ops/<ツール名>/` の TypeScript CLI にし、`npm run ops:<ツール名> -- <コマンド>` で実行する。`tools/pricing/` と同じく `tsx` で動かし、型検査・lint・Knip・構造検査の対象に入れる。依存の向きは既存どおり（tools は content・i18n・routing・lib だけを使う）。
- 公開サイトから `tools/ops/` を読み込まない。`out/` には何も足さない。
- 共通部分は `tools/ops/shared/` に置く（データの読み書き、CSV、日付、CLI 引数、書面の出力）。
- テストは Vitest で `tests/ops/` に置き、`npm test` に含める。フィクスチャは架空のデータだけを `tools/ops/fixtures/` に置く。
- 依存パッケージは足さない。CSV は RFC 4180 の範囲を自前の小さな関数で読み書きし、JSON の形は既存の `zod` で検証する。

### 実データの置き場所

- 既定は `<repo>/.data/`（`.gitignore` に追加）。`--data <dir>` か環境変数 `TSUMUGI_DATA_DIR` で変えられる。
- 書き込み先がリポジトリ内の `.data/`・`.artifacts/` 以外になる指定は、ツールが拒否する。追跡対象のディレクトリへ実データを誤って書かないため。
- JSON は一時ファイルに書いてから置き換える。途中で止まっても壊れたファイルを残さない。
- ID（顧客・案件・見積番号など）は英小文字・数字・ハイフンに限る。ファイル名にそのまま使うので、`..` や区切り文字を通さない。

### 見積もり（#25）

- 金額はすべて `src/content/prices.ts` から引く（`productionPlans()`・`RUN`・`OPTIONS`・`EXTERNAL_MONTHLY_ESTIMATE`・`paymentSchedule`・`withTax`）。手入力の金額は受け付けない。
- `OPTIONS` に安定したキー（`page_add` など）と `firm` を足した。添字でオプションを引くと、並べ替えたときに別の金額を引く（`RUN`・`BUILD` と同じ事故の予防）。`firm: false` は、料金表に「別見積もり」「着手前に総額を確定」とある出張撮影の 2 件。表示は変えない（`price.tsx` は `name`・`price`・`note` だけを使う）。
- 各行に確定度を持たせる：`fixed`（確定）、`reference`（別見積もりの目安）、`provisional`（仮置き）。外部費は料金表でも仮置きなので、常に `provisional`。1 行でも確定でなければ、見積もり全体を「未確定を含む」とし、書面の冒頭に注意を出す。
- 支払方法は `deposit_acceptance`（着手時・検収時の 2 回、`paymentSchedule`）だけを受け付ける。自社の分割払いは料金表・規約で新規受付をしていないため、入力の段階で拒否する。オプションの請求時期は規約に定めがないので、書面では「ご契約時に確定」とし、未確定の事項に自動で入れる。
- 消費税は請求の回ごと（着手時・検収時・オプション・毎月）に `withTax` で計算する。合計に一度だけ掛けた額と 1 円ずれることがあるので、そのずれを隠さず、書面にも計算方法を書く。
- 受付準備中のプラン（`preparing: true`）は計算できるが、保存（発行）を止める。
- 見積もりは `.data/estimates/<見積番号>.json` に版を重ねて保存する。各版は入力と計算結果の写しを持つ。保存後に料金表が変わっても、発行済みの版の金額は変わらない。料金表の金額だけから作る指紋を一緒に保存し、書面の出力時に料金表が変わっていれば注意を出す。前の版と同じ内容、有効期限を過ぎた見積もりは保存しない。
- 書面は同じ中身から Markdown と印刷用 HTML を作る。HTML は `<script>`・イベント属性・外部読み込みを含めず、文字列はすべてエスケープする。PDF 化はブラウザの印刷に任せ、ツールはブラウザを起動しない。
- 版の差額は、明細（追加・削除・変更）と合計（初期費用・毎月・期間の総額、税別と税込）で出す。2 版目以降の書面には前の版からの変更を載せる。

## 残したこと（オーナーの判断が要る）

- 外部費の仮置き（月 3,500 円）を案件ごとの確定額に置き換える入力。「金額は prices.ts だけから引く」を優先して今回は作らない。置き換える場合は、出所（契約先・確認日）を必須にする形を別途決める。
- 増築時の制作本体額の充当（規約：12 か月以内・1 回）。前の契約の実績と紐付ける必要があり、顧客管理（#27）の契約記録と合わせて扱う。
- 見積書の発行者欄（屋号以外の住所・連絡先・登録番号）。確定していない値を書面に入れない。
- 画面での入力・共有、顧客ごとの閲覧権限。ホスティングと認証方式の決定後に扱う。
