# 0025 — 検査レポートを検証したビルドに紐付け、実測値に記録日を添える

日付：2026-09-16。状態：採用。関連：[#34](https://github.com/bright-broom/tsumugi/issues/34)、[ADR 0012](0012-root-project-layout.md)。

## 背景

- `works.html` の検査件数は `verify-report.json` の `pass` だけを読み、失敗の有無・測定日時・対象のコミットを確かめていなかった。別のコミットや FAIL を含む実行の数字でも表示できた。
- LCP は `src/content/measurements.ts` の固定値（0.18 秒）で、更新は `verify --write` だけ。一方ページは「公開前の検査結果」「手で書いた値ではありません」と書き、ビルドのたびに測った数字に読めた。0.18 秒は旧版の検査で記録された値で、リポジトリに初めて入ったのはコミット `a8151e6`（2026-09-14 日本時間）。ヒーロー画像の追加など、その後にページ構成が変わっている。
- Vercel の Git 配備は静的検査だけで、全項目のレポートを配備に渡す手順はない。

## 決定

### レポート（スキーマ v1）

`tools/verify/report.ts` が書き、`src/lib/verification-report.ts` の zod スキーマで読む。

| 項目 | 内容 |
|---|---|
| `kind` / `mode` | `full`（静的＋ブラウザ）か `static`、`preview` か `production` |
| `measuredAt` | 測定日時（ISO 8601） |
| `commit` | `sha`（`GITHUB_SHA` → `VERCEL_GIT_COMMIT_SHA` → `git rev-parse HEAD`）、取得元、`dirty`（未コミットの変更。git の HEAD が同じコミットのときだけ判定し、分からなければ `null`） |
| `artifact` | 検査した `out/` のファイル数と、全ファイルの内容から作った SHA-256 |
| `counts` / `verdict` | PASS・WARN・FAIL・対象なし（N/A）の件数と判定 |
| `lcp` | ブラウザ実測の最悪値とページ数（静的検査では `null`） |
| `acceptance` | 仕様 20 項目ごとの受入の状況（[ADR 0026](0026-acceptance-mapping.md)） |

### ページに件数を出す条件

`adoptReport(report, currentCommit)`（純粋関数）が次をすべて満たすときだけ採用する。満たさなければ理由を返し、`works.html` は件数を「—」、説明を「このページと同じコミットで全項目を検査した記録がない」にする。

1. スキーマに合い、件数と判定が結果の行と一致する（手で書き換えた数字を使わない）
2. `kind` が `full`
3. FAIL が 0
4. レポートとビルドのコミットが同じで、どちらも `dirty === false`（分からない場合も採用しない）

古さはコミットで判定する。同じコミット・変更なしなら、成果物は同じソースから作られている。採用したときは、件数に加えて検査日（日本時間）・コミットの先頭 7 文字・PASS / WARN を本文に出す。

### LCP の表示

仕組みはビルドごとの再測定に変えず、**表示を実際の更新方法に合わせる**。

- `measurements.ts` に `LCP_RECORDED_ON` を足し、`verify --write` が値と一緒に記録日（日本時間）を書く。
- `works.html`・`spec.html` は「手元での実測（YYYY-MM-DD 記録）」と書き、ビルドのたびに測り直した数字ではないと明記する。
- 現在の記録日は、上の履歴から確かめられる `2026-09-14`。現在のページ構成で測り直すには、ブラウザ実測ができる環境で `npm run verify -- --write` を実行してコミットする（この作業環境ではブラウザ実測を実行できなかった）。

### 配備の経路と表示

| 経路 | 結果 |
|---|---|
| Vercel の Git 配備（`npm run validate`、静的検査だけ） | 全項目のレポートが無いので「—」 |
| Vercel のビルドに全項目のレポートが紛れ込んだ場合 | git が無く未コミットの変更を判定できないので「—」 |
| GitHub Actions（全項目を検査するが配備しない） | 配備物に影響しない |
| 同じコミットのきれいなチェックアウトで `build → verify → build` し、その `out/` を配る | 件数・検査日・コミットを表示 |

最後の経路（検証済みの `out/` をそのまま配る配備、Vercel なら prebuilt 配備）を採るかはオーナーの判断で、この変更では配備の手順を追加・実行していない。

## 検証

- 単体：コミットの判定（CI・Vercel・手元・不一致・不正な値）、採用の条件と理由（静的のみ・FAIL あり・別コミット・変更あり／不明・件数の改ざん・旧形式）。
- 結合（`tests/verified-build.test.tsx`）：verify と同じ組み立てでレポートを置き、ビルド時の読み込みを通して `works` を描画する。Vercel の Git 配備では「—」、同じコミットのきれいなチェックアウトではレポートと同じ件数・日付・コミット、別コミット・FAIL・未コミットの変更では「—」。`works`・`spec` が LCP の記録日を出すこと。
- 配布物の差分は `works.html`・`spec.html` の 2 ファイルだけ（残り 48 ファイルは SHA-256 が一致）。
