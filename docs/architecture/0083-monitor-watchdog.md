# 0083 監視そのものが動いているかを見張り、復旧まで知らせる

- 日付：2026-09-24
- 状態：採用（実際の起票・復旧の連絡は、main 反映後の実行で確認する）

## 背景

監査 A07「監視の停止自体の検知、複数担当への通知、復旧通知がない」。

毎時の監視（Site monitor、[ADR 0064](0064-production-monitoring.md)）は、FAIL でジョブが失敗し、GitHub の標準の通知が届く。ここには 3 つの穴があった。

- **止まっていることが分からない**。2026-09-18 の監査では、実行が success でありながら Monitor を含む全手順が skipped だった。ジョブの成否だけを見る運用では、監視できていないことに気づけない。定期実行はワークフローの無効化でも止まる。
- **復旧が伝わらない**。失敗の通知は届くが、直ったことは誰も知らせない。記録（`operations.md` の「障害と復旧の記録」）が人の記憶に依存する。
- **通知が 1 人に閉じる**。定期実行の失敗通知は cron を最後に変更した人にだけ届く。

## 判断

`npm run watchdog`（`tools/ops/watchdog.ts`・`cli/watchdog.ts`）と、6 時間ごとのワークフロー `monitor-watchdog.yml` を追加する。監視の**結果**ではなく、監視の**実行の履歴**を検査する。

- **監視の実行**：直近の完了した実行が `--max-age-minutes`（既定 720 分。当初は 180 分、下の追記を参照）より古ければ FAIL。一度も実行されていない場合も FAIL。
- **監視の中身**：直近の実行の手順に `Monitor` があり、`skipped` でないことを確かめる。手順が改名されれば「実行に含まれていません」で止まる。手順を取得していないときは SKIP（分からないものを合格にしない）。
- **直近の結果・連続の失敗**：success 以外は FAIL。2 回以上続けば別の FAIL として出す。
- **復旧**：直近が成功で、その前が失敗なら「復旧」を PASS として出す。
- **通知**：判定は `down`・`recovered`・`none` の 3 つに畳む。ワークフローは `down` で `site-monitor-down` ラベルの issue を **1 件だけ**立て（既にあれば追記）、`recovered` でそれを閉じる。issue はリポジトリを見ている全員に届き、リポジトリ変数 `ALERT_ASSIGNEES` で担当者を割り当てられる。

判定は純粋関数に置き、GitHub との通信・起票・クローズはワークフローに置く。手元では `--runs <実行履歴.json>` で通信せずに試せる。

## 追記（2026-09-26）既定を 12 時間にし、「止まっている」警報も閉じる（#101）

運用を始めてすぐ、`site-monitor-down` の issue（#101）が立ち、6 時間ごとに追記され続けた。中身はすべて「直近の実行は 3〜4 時間前。180 分より古い」で、**監視の実行自体はすべて成功していた**。

- **原因 1：閾値が GitHub の実際の動きに合っていない。** cron は毎時（`17 * * * *`）だが、GitHub Actions の schedule は混雑時に遅れ・間引かれる。2026-09-19〜26 の実行履歴（約 60 回）では、間隔は 2.4〜6.3 時間で、毎時に届いたことは一度もない。180 分の閾値では正常な運用が常に警報になり、本当の停止が埋もれる。
- **原因 2：「止まっている」警報が閉じない。** issue を閉じる条件が `recovered`（前回が失敗で今回が成功）だけだった。止まっていた監視は失敗の実行を伴わないので、動き出しても `none` のままで、issue は開いたまま残る。

判断：

- 既定の閾値を **720 分（12 時間）** にする（`DEFAULT_MAX_AGE_MINUTES`）。実測の最大の約 2 倍。見張りは 6 時間ごとなので、本当に止まったときは最長で約 18 時間で気づく。毎時の検知をあきらめる代わりに、警報が出たら本物という状態を取る。
- ワークフローは `down` 以外（`recovered`・`none`）で開いている警報の issue を閉じる。
- 実行が止まっているときの本文は、失敗の中身（死活・証明書…）ではなく、ワークフローの有効状態（60 日無活動での自動停止など）と手動実行を案内する。
- **監視の実際の頻度は「毎時」ではなく 3〜6 時間おき**であることを operations.md に明記する。より短い間隔で見る必要があるなら、GitHub の外の監視（A07 の残り）で補う。

## 限界

- **同じ GitHub Actions の上で動く**。GitHub 全体の停止、Actions の停止、リポジトリの設定変更でワークフローごと止められた場合は検出できない。外部からの独立した監視（別サービス・別アカウント）は、費用と運用の担当を決めてから（監査 A07 の残り）。
- 通知の経路は GitHub の issue と Actions の通知だけ。メール・電話・LINE への転送は、受信の確認ができてから足す。
- 起票・クローズは実際の実行で確かめていない（この作業環境から GitHub へ接続できない）。main 反映後に `workflow_dispatch` で一度動かして確認する。
- 監視先そのものの正しさ（何を見るべきか）はここでは変えていない。ADR 0064 のまま。
