# 0039 — leadfinder は取り込んだ CSV だけを扱い、GBP は手で書き出した情報との突き合わせと承認の記録にする

日付：2026-09-16。状態：採用。関連 Issue：[#24](https://github.com/bright-broom/tsumugi/issues/24)（leadfinder）、[#30](https://github.com/bright-broom/tsumugi/issues/30)（GBP の紐付け・情報同期・投稿と口コミ対応）。共通の置き場所・データの扱いは [ADR 0036](0036-internal-ops-tools-and-estimates.md)。

## 背景

ガイドライン 4.1 は、営業リストを `leadfinder` で作り、優先度を「口コミ数 45 ＋ 評価 20 ＋ 電話番号 20 ＋ サイト状態 15」とする。同時に、Places API のコンテンツは恒久保存できず、`place_id` 以外は 30 日以内に破棄すると定めている。配点は受注実績ではなく仮説で、商談 10 件で調整する。

GBP については、紐付け・情報の同期・月次の投稿・口コミ返信をサービスに含める。API 連携か手作業かは決まっていない。どちらでも、承認なしに投稿・返信しないことが前提になる。

この作業では外部 API を呼ばず、スクレイピング・自動送信もしない。

## 決定（#24 leadfinder）

- 入力はオーナーが用意した CSV だけ（列：`name` 必須、`phone`・`website`・`industry`・`area`・`rating`・`review_count`・`place_id`）。取り込みごとに**入力元**と**収集日**を必須にし、**保存期限（日数）か期限なし**のどちらかを明示させる。利用条件の判断はオーナーが行い、ツールは既定値で済ませない。
- 台帳 `leads/ledger.json` には、情報源ごとの観測をそのまま残す。統合した値・評価は毎回計算する（どの情報源の値かを失わない）。同じ内容のファイルの再取り込みは拒否する。
- 正規化：電話は NFKC・数字だけ・`+81` を 0 に戻し、10〜11 桁かを確かめる。URL は `www.`・末尾の `/`・クエリを除いて比べ、http(s) 以外は読まない。店名は NFKC と空白、法人格（株式会社など）の有無をそろえて比べる。
- 重複：`place_id`・電話・URL（ポータルのトップだけのものは除く）のどれかが同じなら 1 件にまとめる。別々の見込み客をつなぐ観測が来たら統合し、要確認にする。**店名と地域だけが同じ候補は統合しない**（支店などを取り違える）で、要確認として示す。情報源で店名・電話・サイトが食い違えば要確認にする。
- サイト状態：URL なし＝サイトなし、食べログ・Instagram・ホットペッパー・LINE のドメインだけ＝ポータル依存（ガイドライン 4.1）、それ以外＝自社サイトあり。
- 評価：ガイドラインの配点をそのまま使い、項目ごとに点数と根拠を持たせる。口コミ数は「満点とする件数」までの比例（既定 100 件、`--review-cap` で変更）、評価は 1〜5 を 0〜20 点に比例させる。**どちらの曲線もガイドラインに定めがないための仮置き**で、根拠の文言にも仮置きと書く。未取得の値は 0 点にして要確認にする。
- 状態：未確認・要確認・確認済み・対象外。確認済みでも新しい観測が加われば要確認に戻す。対象外は対象外のまま。
- 絞り込み：業種・地域（部分一致）、点数、状態、サイト状態。
- CRM への CSV：確認済み（指定すれば要確認も）だけを出し、評価の根拠・入力元・保存期限を列に入れる。先頭が `=` `+` `-` `@` のセルは `'` を付けて、表計算ソフトで式として実行されないようにする。
- 保存期限：期限を過ぎた値が残っている間は出力しない。`purge` で `place_id` 以外を捨て、自分で確認・ヒアリングしたメモ（確認の記録）は残す。

## 決定（#30 GBP）

- 突き合わせ：サイト側（顧客サイトの店舗情報）と GBP 側（管理画面の表示を手で書き出したもの）を同じ形のプロフィール JSON にし、店名・住所・電話・ウェブサイト・予約先・曜日ごとの営業時間・臨時営業時間を比べる。結果は「一致」「表記ゆれ（正規化すれば同じ）」「不一致」「片方だけ」。ウェブサイト・予約先の比較が、GBP とサイトの紐付けの確認になる。不一致・片方だけがあれば終了コード 2 を返す。
- 変更：直す値と、直す側（GBP かサイトか）を提案として記録し、承認（誰が・いつ）を経てから反映（誰が・いつ・確認方法）を記録する。承認のない変更は反映済みにできない。
- 投稿・口コミ返信：下書き → 承認 → 実施の記録。承認時に文面の SHA-256 を記録し、実施の記録は「承認済み」かつ「承認した文面と現在の文面が同じ」ときだけ受け付ける。承認後に文面を直すと承認は外れる。口コミ返信は対象の口コミの特定を必須にする。期日を過ぎた未実施を一覧に出す。
- **ツールには GBP へ投稿・返信する経路を作らない。** 「実施」は人が GBP で行った後の記録だけ。

## 残したこと（オーナーの判断が要る）

- 営業リストの入力元・収集方法・利用条件（#24 の完了条件の 1 つ目）。Places API を使う場合の規約の確認、30 日の保存期限の運用、個人情報の扱い。ツールは期限の明示と破棄の仕組みまで。
- 評価の曲線（口コミ数・評価の配点の配り方）。商談 10 件の結果で調整する。
- 連絡先の自動収集・自動送信の範囲。今回は作っていない。
- GBP の API 連携か手作業かの方式と、責任者（#30 の完了条件の 4 つ目）。API を使う場合も、投稿・返信は承認済みの記録を前提にする。
- サイト側のプロフィールを顧客サイトの設定から自動で作ること。店舗情報の共通設定（#22）が決まってから、変換を足す。
- 投稿の月あたりの回数などの目標。現在の料金表の文言に回数の定めがないため、ツールに回数を入れていない。
