# 0072 — 社内CLIの読み込みから保存までを排他制御する

日付：2026-09-18。状態：採用。関連：#26 #27、監査D02。

## 問題

保存は一時ファイルをrenameするため途中のJSONは露出しない。しかし、複数プロセスが同じ旧版を読み、それぞれ保存すると先の更新が消える。書き込みだけのロックでは読み込みと保存の間の競合を防げない。

## 決定

- 社内CLI共通のrunCliで、コマンド開始前に保存先直下の`.ops-lock`を排他的に作る。requests/crm/estimate/metrics/report/leads/gbpの7入口に適用する。
- 保存先全体を単位とし、読み込み・検証・更新・保存・書き出しを含め、同期コマンドが戻るまで保持する。読み取りコマンドも途中の更新と混在させないため同じ制御を使う。help・未定義コマンドはロック取得前に戻す。
- 保存先は既存の制約で検証し、実パスに正規化。同じディレクトリの別名でも同じロックへ集約。別の保存先は別の操作単位。
- 競合時はOpsErrorで終了1。待機・自動再試行・古いロックの自動削除はしない。呼び出し元は実行終了を確認後に再実行する。
- ファイルは0600、親の新規作成は0700。PID・ホスト・開始日時を記録。秘密情報や顧客データは記録しない。
- 正常/例外終了時に解放する。現在のパスのdevice/inodeが自分の取得した通常ファイルと一致するときだけ削除し、手動で置き換えられたファイル・リンクは保持する。

## 適用範囲と限界

単一端末のローカルファイルシステムで、この共通CLIを使う協調的なプロセス間の排他である。認証・利用者権限・監査ログ・複数端末の共有ストレージ・HTTPサービス・手編集は対象外。異なる保存先から同じ外部`--out`へ出力する操作も同一ロックにはならない。

複数ファイルの更新を一括で取り消すトランザクションではない。既存の各ファイルの原子的置換は維持する。コマンドは現状すべて同期処理で、今後非同期化する場合はawait完了までロックを保持する設計に変更する。

強制終了ではロックが残り、後続は停止する。タイムスタンプやPIDが古いだけで削除しない。運用手順に従って実行元とプロセスの停止を確認する。これは多人数運用の認証認可を実装したことにはならず、D02全体は継続する。

## 検証

正常・例外解放、重複実行時にコールバックが走らないこと、別プロセスで7CLIすべてが停止すること、実CLIの解放後の再実行、古いロック・壊れたリンク・別名パス・置換されたロック、helpの表示を確認。全体検証はstatus.mdを参照。
