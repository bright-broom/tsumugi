# 0068 比較元の公開成果物と配信内容を全ファイルで照合する

- 日付：2026-09-18
- 状態：採用（main 反映は status.md 参照）

## 背景

監査 A05。現行監視はHTTP応答・ページ一覧・canonical・JS・受付リンクなどを確認するが、古い本文・CSS・画像の一部混在は識別できない。まず指定した成果物と公開内容の一致を機械的に確認し、配備IDやコミットとの紐付けは別の証跡として扱う。

## 判断

check:release は比較元ディレクトリを必須にし、全ファイルの相対パス・バイト数・SHA-256から比較元の指紋を作る。HTML・CSS・画像などをバイナリで照合し、index.html と公開トップ / は別に確認する。HTTP200を要求し、404.html だけは404応答でも内容が同一なら合格とする。転送は追跡しない。

同時取得は最大4、各リクエストは15秒で打ち切る。本文が比較元より大きくなったら読み取りを止める。隠しファイル・シンボリックリンク・index.html がない比較元は通信前に拒否する。比較元の上限は1000ファイル・各64MiB。取得失敗や不一致があっても残りを調べ、全結果をJSONに保存する。fingerprint を指定した場合は比較元の取り違えを通信前に止める。

served-dist は通信しない模擬配信。結果の題名に明示し、本当の公開先の検査と混同しない。全一致は終了0、配信不一致は1、比較元や入力の問題は2。

## 運用と限界

公開時に使用した実際の成果物を比較元にする。別時点の再ビルドは、works.html の検証表示などが変わり得るため同じコミットでも同じバイト列とは限らない。コマンドはコミット・配備IDを推測せず、署名や第三者の真正性証明とも扱わない。古い版の成果物を指定すれば、その版との一致を確認する。

これでA05の成果物一致の判定を実装するが、Vercelの配備ID・production alias・commitをAPIで照合することは残る。A06の資産欠落の一部も検出できるが、毎時のmonitorへの組込、CSS/画像のContent-Typeやセキュリティヘッダー、比較元にない余分な公開ファイルの探索は別課題。既存check:live・monitor・セキュリティ検査を併用する。取得中に公開内容が切り替われば混在として失敗し得るため、切替完了後に再検査する。

## 検証

バイナリ一致、同じ長さの旧HTML/CSS、画像欠落、トップの別URL、404、転送拒否、通信失敗、同時接続上限、過大応答打切り、比較元指紋の不一致、隠しファイル／リンク／index欠落、CLIの終了コードと模擬配信表示を確認する。実際の出力一式を使う検査と全体検証は [status.md](../status.md) に記録する。
