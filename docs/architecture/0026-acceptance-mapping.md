# 0026 — 納品仕様 20 項目と受入検査を対応付け、証明にならない PASS を数えない

日付：2026-09-16。状態：採用。関連：[#35](https://github.com/bright-broom/tsumugi/issues/35)、[ADR 0024](0024-publication-gates.md)。

## 背景

- `spec.html` は「20項目すべてを自動でチェックする仕組み」と書いていたが、検査は項目の一部しか見ていなかった。例：画像が 0 枚のページでも「07 imgのalt」が PASS（`0枚すべてalt有り`）、「05 業種別ページ」は 4 ページの有無だけで、電話とフォームの主役の入れ替えは見ていない。Google ビジネスプロフィール・通知 2 系統・口コミの運用はまったく検査していない。
- 20 項目と検査の対応がどこにもなく、対応漏れに気づく仕組みもなかった。

## 決定

### 対応表

`tools/verify/acceptance.ts` の `ACCEPTANCE` に、項目ごとに「自動検査の検査名（静的／ブラウザ）」「人の確認」「外部接続の確認」「対象外として記録してよい条件」を持たせる。項目の ID と、ページに出す確認の方法（`check`）は `src/content/spec.ts` に置く。

| 方法 | 項目 |
|---|---|
| 自動検査 | 13 LCP、14 先頭画像 |
| 自動検査＋人の確認 | 1 電話、2 営業時間、3 住所・地図、4 料金、5 電話とフォームの主役、7 写真、12 スマホとPCの内容、15 スコアを追わない、16 タップ領域、17 構造化データ |
| 人の確認 | 6 対応エリア、8 スタッフ紹介、9 実績、10 お客様の声、11 料金・選び方の説明 |
| 外部接続の確認 | 18 ビジネスプロフィール、19 通知 2 系統、20 口コミの運用 |

`verify` は最後に「受入 対応表」を記録する。次のどれかがあれば FAIL。

- 対応表に無い項目、確認の方法が 1 つも無い項目、仕様のページに無い項目
- 対応表から導いた方法と、ページに出す `check` が一致しない（検査していない項目を「自動検査」と表示しない）
- その実行に存在しない検査名（`--static` のときはブラウザの検査名を求めない）

### 人の確認・外部接続の記録

- `src/content/acceptance.ts` の `ACCEPTANCE_RECORDS` に、確認日・確認者の立場・結果（`confirmed` / `not-applicable`）・根拠の置き場所を記録する。**いまは空**。
- 対象外（`not-applicable`）は、対応表に対象外の条件がある項目だけ受け付ける。未来の日付や根拠の無い記録は無効。
- 本番モードでは、人の確認が必要な項目（自動検査だけの 2 項目以外の 18 項目）に有効な記録が無ければ FAIL（ADR 0024 の `ACCEPTANCE_RECORDS`）。
- レポートの `acceptance` に、項目ごとの自動検査の状態（`pass` / `fail` / `not-run` / `no-target` / `none`）と記録の状態を残す。

### 証明にならない検査の扱い

- **対象なし（N/A）を新設**：画像が 0 枚のページの「07 imgのalt」「14 先頭画像にlazyを付けない」は N/A として記録し、PASS に数えない。現在は 21 ページ中 20 ページが該当し、静的検査の PASS は 40 件減る（検査の条件は緩めていない）。
- alt の判定を `alt=` を含むかから属性として持つかに変え、`data-alt` だけの画像も FAIL にする。
- 「01 電話番号」はヘッダーの中にも `tel:` リンクがあることを必須にした（上部に置く約束の一部。各画面幅で見えているかは人の確認）。
- 「05 業種別ページ」の詳細に、ページの有無だけを見ていることを明記し、主役の連絡手段は人の確認に回す。

### 仕様のページの文言

- 「20項目すべてを自動でチェック」をやめ、「自動で検査できる部分は検査スクリプトで、それ以外は人が確認して記録を残し、1つでも満たさなければ納品しません」に改めた。
- 各項目の説明の下に、確認の方法（自動検査／自動検査と人の目での確認／人の目で確認し記録／外部サービスで実際に動かして確認し記録）を出す。
- 「このサイトも上の20項目で作って、同じ検証をかけています」を、「納品するサイトと同じ自動検査をかけています」に改めた。

## 境界

- 「顧客・プラン別に必要な写真・事例・記事・導線の欠落を検出する」は、顧客ごとのプロフィール（業種・プラン・来店の有無）と、事例・記事などの機能（#16〜#22）が無いため自動化していない。現状は人の確認の記録で扱う。機能ができたら、該当項目の `static` に検査を足し、対応表の検査で方法の表示も切り替える。
- 自社サイトについて、どの項目を対象外にするか（例：来店を受け付けないので地図・駐車場は対象外）は事業の判断なので、記録を推測で作っていない。

## 検証

- Vitest：20 項目の網羅と表示との一致、外部接続を自動検査済みにしないこと、対応漏れ・検査名の誤り・表示の食い違い・方法の無い項目の FAIL、記録の有効性、レポートの状態、画像 0 枚の N/A、`spec` の表示ラベルの件数。
- `npm run verify -- --static`：「受入 対応表」PASS（20項目：自動 2・自動＋人 10・人 5・外部接続 3）、PASS 319 / WARN 1 / FAIL 0 / 対象なし 40（変更前は PASS 358 / WARN 1 / FAIL 0。差は N/A への移動 −40 と対応表 +1）。

### 2026-09-17：自社サイトの公開指示

[ADR 0056](0056-owner-authorized-publication.md) により、紬の自社サイトはオーナーの公開判断を独立して記録する。記録の範囲内の未実施確認を WARN として残し、専門家確認・納品検収の完了とは区別する。顧客案件は従来の条件を維持する。
