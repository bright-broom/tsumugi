# 本番検査の WARN 3 件：未記録の確認と、解消の手順

`npm run verify -- --mode production`（Vercel の本番配備では自動で本番モード）は、紬の自社サイトで **PASS / WARN 3 / FAIL 0** になる。この 3 件は不具合ではなく、**人が確認して記録すべきことが、まだ記録されていない**ことを示す。2026-09-19 の main `fa8a67b` で確認した内容。

| #   | 検査の対象              | 何が未記録か                                                                                            | 解消する人                           |
| --- | ----------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 1   | `LEGAL_APPROVALS.terms` | 規約（ご契約とお約束）の専門家確認                                                                      | 弁護士などの専門家 → 記録はオーナー  |
| 2   | `LEGAL_APPROVALS.legal` | 特定商取引法に基づく表記の専門家確認                                                                    | 同上                                 |
| 3   | `ACCEPTANCE_RECORDS`    | 納品仕様 20 項目のうち、人の確認・外部接続の確認が要る **18 項目** の記録（1 件の WARN にまとめて表示） | オーナー（外部サービスの確認を含む） |

## なぜ FAIL ではなく WARN なのか

本番モードでは、この 3 つは本来 **FAIL**（公開・納品させない）になる（[ADR 0024](../architecture/0024-publication-gates.md)）。紬の自社サイトだけは、オーナーが未確認を承知で公開を指示した記録 `OWNER_PUBLICATION`（`src/content/publication.ts`、[ADR 0056](../architecture/0056-owner-authorized-publication.md)）があるため、次の条件をすべて満たす間だけ WARN に下げている（`tools/verify/publication.ts`）。

- 公開承認のドメイン・事業者名（SHA-256）が、現在の設定と一致する。
- 承認したときの規約・特定商取引法の表記の文面の SHA-256 が、現在の文面と一致する（`documentHashes`）。
- 未確認の受入項目が、公開承認で「後回しにする」と記録した項目（`deferredChecks`）に含まれている。
- 専門家の承認記録が **全項目とも空** である（一部だけ記入した・誤った記録は WARN にならず FAIL）。

どれかが崩れると FAIL になり、配備が止まる。たとえば規約の文面を変えると `documentHashes` が合わなくなるため、公開判断を記録し直す必要がある。

**WARN は「確認済み」ではない。** 検査の詳細にも「確認済み・納品検収済みを意味しません」と出る。顧客サイトの納品には、この例外を使わない（顧客サイトでは 3 件とも FAIL になり、記録するまで納品できない）。

## サイトでの表示

承認記録が揃うまで、ページに下書きであることを表示している。

- 規約（`/terms.html`）：「この文面は、契約書の下書きです」「専門家による確認は未実施です。**実際のご契約は、確認後の書面で取り交わします。**」
- 特定商取引法に基づく表記（`/legal.html`）：「公開前の確認を進めています」「以下は現在の提供条件をまとめた下書きです。契約条件の確認後に確定します。」

記録が揃うと、この表示は自動で消える。記録が揃ったあとで文面を変えると、プレビューの検査でも FAIL になる（確認済みと表示しながら、確認していない文面を出さないため）。

## 1・2：規約と特定商取引法の表記の専門家確認

|                                                                                                                         | 規約（terms）                                                                                                                                                                                              | 特定商取引法に基づく表記（legal）                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 文面の正本（SHA-256 の対象）                                                                                            | `src/i18n/locales/ja/terms.ts`                                                                                                                                                                             | `src/i18n/locales/ja/legal.ts`。表に出る氏名・住所・連絡先は `src/i18n/locales/ja/config.ts` から入り、**SHA-256 の対象外**（変えても指紋は変わらないため、変えたときは確認をし直す） |
| 現在の文面の SHA-256                                                                                                    | `fc7e1aced92c386f057d1d55a6db8df6e7accba9d0c86d98f38cd7014dda1151`                                                                                                                                         | `0cdf0b0d82546a5b99d58e11a762955a9b7eec047877cce723f5808ecf46eee2`                                                                                                                    |
| 確認してほしい点（[status](../status.md) の残課題・[ビジネスガイドライン](../business/紬_ビジネスガイドライン.md) 8.1） | 2026-09-18 に改定した料金での支払（着手時50%・検収時50%）・変更枠・無償修補・中止と精算・増築時の充当の条件、自社 24 回分割の新規受付をしないこと、フリーランス法第 4 条（書面等による条件の明示）への対応 | 事業者の氏名・所在地・連絡先・料金・支払時期と方法・提供時期・解約や返品に当たる条件の記載が、実際の提供条件と一致しているか                                                          |

SHA-256 は文面（カタログのその部分）から計算した指紋で、`npm run verify -- --mode production` の WARN の詳細に最新の値が出る。**確認を受けた版の値**を記録する。

### 記録のしかた

確認を受けたら、`src/content/config.ts` の `LEGAL_APPROVALS_BY_LOCALE.ja` の該当する文書に 4 項目を記入する。

```ts
terms: {
  version: '2026-10-01 版',        // 確認を受けた文面の版（契約書ひな形の版番号など）
  approvedOn: '2026-10-01',        // 確認を受けた日（未来の日付は FAIL）
  reviewerRole: 'attorney',        // 弁護士は 'attorney'、それ以外の専門家は 'other-expert'
  catalogSha256: 'fc7e1ace…',      // 確認を受けた文面の SHA-256（検査の詳細に出る値）
},
```

- 4 項目が揃うと、その文書の WARN が消え、ページの下書きの表示も消える。
- 指摘を受けて文面を直した場合は、直した後の文面の SHA-256 を記録する（直す前の値のままだと FAIL）。
- 文面を変えると `OWNER_PUBLICATION.documentHashes` も合わなくなる。公開判断の記録（`src/content/publication.ts`）を更新する。
- 確認者の氏名や事務所名はリポジトリに書かない（役割だけを書く）。確認のやり取りの記録はリポジトリ外に保管する。
- **確認を受けていない値を入れない。** 架空の値やテスト用の値で WARN を消すことは、検査の意味を失わせる。

英語など他の言語を公開する場合は、その言語の文面として別に確認し、`LEGAL_APPROVALS_BY_LOCALE.en` に記録する（[ADR 0081](../architecture/0081-build-time-locales.md)）。

## 3：受入確認 18 項目

納品仕様 20 項目（`/spec.html`、`src/content/spec.ts`）のうち、自動検査だけでは証明できない部分を、人の確認・外部接続の確認として記録する（[ADR 0026](../architecture/0026-acceptance-mapping.md)、対応表は `tools/verify/acceptance.ts`）。自動検査だけで完結する 2 項目（`lcp` 表示速度、`first-image` 先頭画像）は対象外で、残り 18 項目が未記録。

紬の自社サイトでは、たとえば来店の有無（`address`）・掲載できる実績（`cases`、現在の事例は自社サイト 1 件）・お客様の声の有無（`voices`）・ビジネスプロフィールの有無（`business-profile`）・問い合わせ手段（`notifications`、自社はメールと電話の受付で、フォームの二重通知は使っていない）で、「確認済み」か「対象外」かが変わる。**どちらにするかはオーナーが実物を見て判断する**（この文書では決めない）。

### 記録のしかた

`src/content/acceptance.ts` の `ACCEPTANCE_RECORDS` に、項目ごとに記入する。

```ts
export const ACCEPTANCE_RECORDS = {
  phone: {
    checkedOn: '2026-10-01', // 確認した日（未来の日付は無効）
    checkedBy: 'owner', // owner・staff・customer
    outcome: 'confirmed', // 満たしている＝confirmed、対象外の条件に当てはまる＝not-applicable
    evidence: 'docs/acceptance/2026-10-01-phone.md', // 根拠の置き場所（確認メモ・テスト送信の記録・画面の記録など）
  },
};
```

- `not-applicable` は、上の表の「対象外にできる条件」がある項目だけに使える。条件がない項目に書いても未記録のまま扱う。
- `evidence` は空にできない。確認の根拠をリポジトリの文書か、リポジトリ外の保管場所として書く。個人情報（お客様の連絡先など）は書かない。
- 記録した項目は、その日から WARN の対象から外れる。18 項目すべてが記録されると `ACCEPTANCE_RECORDS` の WARN が消える。
- 外部接続の 3 項目（`business-profile`・`notifications`・`reviews`）は、実際に動かした記録（テスト送信の到着、プロフィールからの移動）を根拠にする。
- 記録を増やしても、公開承認の `deferredChecks` を直す必要はない（未記録の項目が `deferredChecks` に含まれていればよい）。未記録の項目を新しく増やす変更をした場合は、公開判断の記録を更新する。

## 優先順位

1. **規約（terms）の専門家確認**：新しいお客様と契約する前。改定した料金・支払・修補・中止の条件が契約の中身になるため。
2. **特定商取引法の表記（legal）**：規約と同時に確認するのが効率的。
3. **受入確認**：外部接続の 3 項目（実際の到着・移動の確認）と、実機での操作確認（`no-score-chasing`）を先に。自社サイトの内容を変えたときは、該当する項目を確認し直す。
